<objective>
Give every exercise one synced equipment type and make ⬆ Add weight move by that type's step.

- The type is stored on the registry row (EQUIP-01).
- Migration 19 defaults it from the name and persists it (EQUIP-02).
- The step follows Ian's rack and stacks (EQUIP-04, amended: D-08, D-10, D-17).

weight Ian's rack doesn't make the next step. This plan is the data model and the step seam that Plans
09-02 (sync), 09-03 (rounding and plates) and 09-04 (the Settings and Log UI) build on.

<identity_model>
This phase turns a derived thing (equipment guessed from the name on every read, via `barStyle`/`BAR_FOR`)
into a chosen, synced field. Which wins when the guess and a stored value disagree:

- A stored `equip` that is in EQUIP_TYPES always wins over the guess. equipOf reads the stored value
  first.
- The guess is used only when the stored value is missing, empty, not in the enum, or the name has no
  registry row.
- Between two stored copies of one row, the higher `equipAt` wins: 0 = a default (from the migration or
  exEnsure), Date.now() = Ian's choice. That comparison lives in Plan 09-02's merge.
- Renaming a row never re-guesses its type. The stored value stays until Ian changes it.
- A row whose stored value is invalid reads as the guess for its current name.
</identity_model>
