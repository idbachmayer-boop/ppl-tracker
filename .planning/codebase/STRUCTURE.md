## Naming Conventions

**Files:**
- Single-file app: `index.html` (no build artifact fragmentation)
- Service worker: `sw.js` (standard convention)
- Rules: `firestore.rules` (Firebase naming)
- Tests: `*.test.js` suffix

**Directories:**
- `.github/` — GitHub Actions (GitHub convention)
- `test/` — Tests (standard convention)
- `.planning/codebase/` — Analysis documents (internal tooling)

**Functions:**
- PascalCase for constructors (none in this codebase; all procedural)
- camelCase for all regular functions: `viewToday()`, `lawnStatus()`, `nextWorkout()`, `mergeDB()`
- Uppercase for constants: `PROGRAM`, `SCHEMA`, `TABS`, `SEQUENCE`, `KEY`
- Prefixed with underscore for private/internal: `_schema` field in DB object

**Variables:**
- `DB` — Global application state
- `TAB` — Current active tab (set by `go()`)
- `subState` — Subtab selections per tab (e.g., weight view: "weekly" vs "history")
- `draft` — In-progress workout session being logged
- `revie wWeekOffset` — Week navigation for history review

**Types:**
- No TypeScript; all runtime checks and optional chaining
- Objects represent domain concepts: `{ id, workout, date, entries, endedAt, deletedAt, mtime }`
- Arrays for collections: `DB.sessions`, `DB.weights`, `DB.cardio`

## Where to Add New Code

**New Feature (e.g., new tracking tab):**
1. Add constant to program definitions (e.g., `const FEATURE_DEFAULTS = [...]`)
2. Add array to `blank()` (e.g., `DB.featureLogs: []`)
3. Add migration in `MIGRATIONS` object for the new schema version
4. Bump `SCHEMA` constant
5. Add view function `viewFeature()` in view section (after line 1400)
6. Add tab to `TABS` array with `{ id:'feature', label:'Feature', render:viewFeature }`
7. Add test cases to `test/app.test.js`

**New View/Screen:**
- Location: Add to `TABS` array in `index.html:1282`
- Implementation: Create `viewFeatureName()` function in view layer (`index.html:1374+`)
- Follows pattern: Returns HTML string built from `DB` and business logic functions

**Business Logic (e.g., new scheduling algorithm):**
- Location: `index.html:533-1320` (state/logic section)
- Pattern: Pure functions that read `DB` and return derived results
- Examples: `mowForecast()`, `nextWorkout()`, `exercisePRs()`
- No side effects; mutations happen in view event handlers

**Utilities & Helpers:**
- Shared utilities: `index.html:742-1008` (date, format, math helpers)
- Exercise utilities: `exKey()`, `exLabel()`, `exRow()`, `exMerge()`, `exSuggest()` in lines 1022-1150
- Plate math: `plateBreakdown()`, `platesText()`, `barWeight()` in lines 909-970

**Tests:**
- Location: `test/app.test.js`
- Pattern: `ok(name, condition, extra)` assertions
- Setup fixtures using `setup(app, { mowedDaysAgo, wateredDaysAgo, wx:{ ... } })`
- Call exported functions via `app.functionName(args)` (exported by harness)
- Clock frozen to 2026-08-07; set `TZ=America/Chicago` for date-sensitive tests

## Critical Rules from CLAUDE.md

These are not conventions; they prevent data loss in production:

1. **Sync is union merge, never overwrite** — Every remote write uses `runTransaction()` + `mergeDB()`, never `set()`
2. **Deletes are soft** — Set `deletedAt`, never splice; filters use `isLive()`
3. **Absence never means "off"** — Store explicit `false`, not a deleted key
4. **Migrations touch and persist immediately** — Set `mtime`, save right after rewriting rows
5. **Derived data uses `saveLocal()`, not `save()`** — `save()` bumps `updatedAt` and triggers push

**Escaping:** Every user string rendered in HTML goes through `esc()`. Exception: `esc()` does NOT escape `'`, so never put user strings inside inline handler quotes. Attribute values are not escaped (known hole).

## Testing & Deployment

**Test Command:**
```bash
npm test
```

Runs `test/app.test.js` via Node. Frozen clock to 2026-08-07, Chicago timezone. Suite must pass; failure blocks CI deploy.

**Deployment:**
1. Push to `main`
2. GitHub Actions runs test suite (failure blocks)
3. Actions publishes to GitHub Pages at https://idbachmayer-boop.github.io/ppl-tracker/
4. User must fully close and reopen app on phone to pick up update (SW versioning)

**Offline First:**
- App works completely offline (view local data, log workouts, edit lawn schedules)
- Firebase sync is background, optional, asynchronous
- Service worker caches `index.html` and `./`; old cache versions dropped on new release
