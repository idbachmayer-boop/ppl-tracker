<objective>
Prove the recipe by using it. Follow it cold, end to end, for a map-shaped collection that is not
`sleep`, on a scratch branch that actually runs `npm test` — then fold everything the walk exposed
back into the recipe and throw the branch away.

Purpose: Dry Run A (plan 03-02) machine-verifies the recipe's data-layer half exhaustively. It
structurally cannot reach the hand-written logging/viewing UI step, and no test can prove "the
recipe, read cold by someone who didn't write it, produces the correct result with no step missing,
wrong, or requiring outside knowledge". That is a human-comprehension claim about prose, and the
only honest instrument for it is someone walking the steps and recording where they got stuck.

Output: a gap list, a recipe with those gaps closed, and a short rehearsal record. No code change
survives this plan.
</objective>

Create a scratch branch from the current HEAD. Name it so it is obviously disposable — something
carrying `scratch` and `dry-run-b`. Work only on that branch.

On it, follow the recipe exactly as written, for a new collection named `supplements`: a map keyed by
ISO date whose inner object holds a boolean per supplement, shaped like `mobilityLog` —
`merge: 'replace-whole'`, `explicitFalse: true`. This shape is chosen because it exercises the six
map-only validation branches and the explicit-`false` merge rule, which is the exact hole
`mobilityLog` fell into and the one a list-shaped rehearsal cannot reach. If Ian has named a
different map-shaped candidate, use his instead and say so — the shape matters, the noun does not.

Walk every numbered step the recipe states, including the hand-written UI step. Build a small
toggle-checkbox view in the shape the recipe describes. Add the tests the recipe's required-test list
names. Then run `npm test` and get it green.

Keep a running gap log as you go. For each entry record: the numbered step you were on, what you
needed, where you actually found it, and the one-line change to the recipe that would have prevented
the detour. Classify each as one of:
- **missing** — the recipe never mentions it;
- **wrong** — the recipe says something that is not true of the shipped code;
- **outside knowledge** — the recipe is correct but assumes something a reader would not have;
- **friction** — findable from the recipe, but slower than it should be.

Be honest about near-misses. A step you got right because you happened to remember it from elsewhere
is an *outside knowledge* gap, not a pass.

When `npm test` is green and the gap log is complete, tear the branch down:
1. Commit the rehearsal work on the scratch branch so nothing is left uncommitted.
2. Switch back to the branch you started on.
3. Delete the scratch branch with a force delete.
4. Confirm `git status --porcelain` prints nothing and that `index.html`, `test/harness.js` and
   `test/app.test.js` are byte-identical to their pre-rehearsal state.

Never push the scratch branch, never merge it, never cherry-pick from it. A shipped `SCHEMA` bump is
one-way — the cloud copy is stamped with the new number and older builds refuse to sync — so a
rehearsal collection reaching `main` would be a real, irreversible change to Ian's device.

Write the complete gap log into this plan's SUMMARY. It is the task's actual output; the code was
only the instrument.
