<objective>
Lead the phase with one thin, production-quality path through every layer the phase changes. Then
build the guard rails every later plan converts under.

Path: Ian taps a tab. The tab button names an action instead of calling a global function, the one
`document` click listener hands the event to `dispatchAction`, the event-keyed `ACTIONS` registry
finds `go`, and the tab switches, exactly as before. That path touches the markup, the listener
registration, the dispatcher, the registry and the domain function. It is proven by a test that
fires the listener the app itself registered.

Before any markup changes, the inventory of every inline handler is captured and committed
(DELEG-01 is an ordering requirement). The completeness ratchet (DELEG-03), the no-new-inline guard
(DELEG-04), the propagation guard (DELEG-05) and the keyboard infrastructure (DELEG-06) land here, so
each later screen batch converts against a suite that already refuses a dropped call site, a double
fire, a string where a number was, or a clickable `div`.

Purpose: delegation fails silently. A dropped call site, a string index or a double fire all look
like "the button does nothing" on the phone. The inline version would have worked or thrown. The
checks are the phase (RESEARCH, Don't Hand-Roll, "Key insight").

Output: the inventory snapshot, a harness that records listeners and exposes the registry, the
dispatcher and registry in `index.html`, the app shell delegated, the zero-specificity button reset,
the F2 test block, and the handler count corrected in the roadmap and requirements.
</objective>

<decisions_recorded>
Calls this plan set makes where CONTEXT.md left discretion to the planner. They bind all six plans
(05-01 … 05-06).

- **Names and placement (Claude's discretion).** The registry is `const ACTIONS` and the dispatcher is
  `function dispatchAction(e)`. Both live in a new section headed `Event delegation (F2)`, placed
  immediately before the `Boot` block, after every other top-level `const` in the file. `ACTIONS` is
  read only when an event fires, and no event can fire before the inline script finishes, so nothing
  reads it at module evaluation. The `COLLECTIONS` placement rule does not transfer (RESEARCH,
  "Why here").
- **Event-keyed registry (D-01).** Each entry maps event type to wrapper:
  `name: { click(el, e), change(el, e), … }`. The dispatcher runs `ACTIONS[name][e.type]` only. A
  flat `name → fn` would run a `<select>`'s handler on both `input` and `change`, and a checkbox's
  three times (RESEARCH Pitfall 2).
- **How `this`, `this.value` and `event` travel (Claude's discretion).** A wrapper receives
  `(el, e)`. `this` becomes `el`, `this.value` becomes `el.value`, and `event` becomes `e`. Wrappers
  decode `data-*` and call the EXISTING function with its EXISTING signature and arity. Wrappers
  never touch `DB` and never call `save()`/`saveLocal()`.
- **Numeric args.** Every numeric `data-*` uses one of the keys `i`, `k`, `idx`, `n`, `d`, `range`,
  and every wrapper reads it as `+el.dataset.key` or `Number(el.dataset.key)`. A test enforces the
  pairing. A plan that needs another numeric key adds it to the test's `NUMERIC_DATA` list in the
  same commit.
- **Enter-to-submit (RESEARCH Pattern 3).** One `enter` action has a `keydown` handler. It lives on
  text inputs only, reads `data-enter` (the name of a click action), checks that name is an own key
  of `ACTIONS`, and runs that action's `click` wrapper with the input element. So the input must
  carry the same `data-*` args as the button it stands in for. No other action has `keydown`. It
  lands in plan 05-03, with its first user (the lawn location search).
- **Helpers that used to receive code strings** (`logRow`, the versions `row`) receive pre-built
  attribute fragments whose action name is a literal at the call site (RESEARCH Pattern 2).
- **No boot-time validator.** The checks live in the test only (RESEARCH, Alternatives).
- **Snapshot (Claude's discretion; D-07).** Stored at `test/fixtures/handler-inventory.json` as a JSON
  array written with one-space indentation, one row per inline handler attribute:
  `{ fn, event, tag, was, occurrence, calls, action }`. Rows are keyed on
  (fn, event, was, occurrence), never on line numbers. The three templated rows get
  `actions: [...]` instead of `action`. The scanner that produced it, `scanInlineHandlers`, lives in
  `test/harness.js`, so the suite scans the live file with the same algorithm.
- **Guard against new inline handlers: yes (Claude's discretion, recommended).** It is broad: any
  `on<letters>=` attribute with any quoting, not only the five DELEG events, because Phase 7's CSP
  blocks every inline handler.
- **DELEG-05 (Claude's discretion).** `index.html` has zero propagation stoppers today (re-verified by
  grep during planning). The guard has an empty, named `REVIEWED_PROPAGATION` allowlist.
- **`swGuard` (Claude's discretion).** Its semantics are kept exactly: `swToggle`/`swClear` each get a
  `pointerdown` wrapper calling `swGuard(e)` unchanged and a `click` wrapper. No listener is passive.
- **Backdrop (D-08).** The Ideas modal backdrop stays a `div` with `data-action="ideasBackdrop"` and
  the `e.target === el` guard. Its keyboard path is the sheet's Close button, and no Escape handler
  is added. The DELEG-06 checks name it as the one reviewed non-button click target.
- **Keyboard set (D-04, D-08, D-11).** Nineteen clickable non-buttons become `<button>`. Block-level
  ones get class `tap`, inline ones (the three href-less links and the activity ×) get class
  `tap-inline`. Inner `<div>`s become `<span>`s with `display:block` merged into their existing
  style. `kicker()` gains an optional second argument; `kicker(text, 'span')` returns the same markup
  as a `display:block` span. It lands in plan 05-03 with its first user. No `role="button"` fallback
  is built, because no site needs it (RESEARCH, Keyboard Operability).
- **Escaping (D-03, D-09).** Every interpolated `data-*` value goes through `esc()`, numbers
  included, because D-03 says "every". Every other `${…}` inside an attribute value on a template
  line this phase rewrites also goes through `esc()` when it carries stored or user data (`value=`,
  `id=`, `placeholder=`, `max=`). Class-name ternaries that yield constants are left alone. A
  file-wide attribute sweep stays with VAL-02.
- **Shared actions** are registered by the first plan that needs them, and later plans reuse them:
  `go`, `exportData`, `reload` (05-01); `goSub` (05-03); `logWeight`, `logPetWeight` (05-04);
  `toggleAcc`, `startWorkout`, `skipDay` (05-05).
- **Rollout (D-05, D-10).** 05-01 is the tracer, followed by the rest of the app shell (RESEARCH's P1
  batch: "the tracer bullet"). Then Settings and Ideas (05-02), Care (05-03), Train without the Log
  tab (05-04), Today (05-05), and the Log tab last and alone (05-06). Every plan edits `index.html`
  and `test/app.test.js`, so they run strictly in sequence.
- **Human verification follows `workflow.human_verify_mode: end-of-phase`.** The planning brief asked
  for a `checkpoint:human-verify` with `autonomous: false` at the end of the Log-tab plan.
  `.planning/config.json` sets `human_verify_mode` to `end-of-phase`, which rules out that task type,
  and project precedent (Phases 3 and 4, observations 16 and 19) records that the config wins. D-06's
  gate is kept intact and blocking in the configured form. Plan 05-06's last task carries two
  `<human-check>` blocks: Claude's keyboard-only desktop pass in the browser pane, then Ian's
