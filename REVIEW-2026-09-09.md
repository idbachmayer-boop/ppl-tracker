## The bug that matters, and why

`viewActive` walks `DB.draft.entries`, `.stairs` and `.extras` without checking any of them, because
`startWorkout()` always builds all three. A draft that arrived any other way — synced from a device
on an older schema, or restored from a hand-edited backup — can be short a field, and a missing
`stairs` throws. The screen it takes out is the Log tab: the one Ian is standing in front of at the
rack.

This was not a new hole. The guard immediately above it in `mergeDB` exists for exactly this reason;
its own comment says a bad `workout` name "would crash viewActive's `PROGRAM[name]` lookup." It was
one field short, and had been for months.

It was found by the new smoke check **on its first run**, which is the point of adding one.

Note the second-order cause: `render()` catches whatever a view throws and shows a friendly
"Something broke on this screen" card. That is right for Ian mid-workout and wrong for the suite —
until this branch, an agent could break `viewHistory()` outright and all 187 checks would still pass.
The failure would surface on the phone.

## Still open — security

**Open signup.** `createUserWithEmailAndPassword` is live on a public site with a public repo, so
anyone can create an account in the Firebase project. The rules isolate their data, but it is Ian's
quota, his billing, and an abuse surface for a feature exactly two people need. **Fix in the console,
not in code:** Authentication → Settings → disable new sign-ups once both accounts exist. App Check
is the heavier alternative.

**Rules not reconciled.** Nobody has looked at what is actually deployed. Diff `firestore.rules`
against the console before deploying it.

**No CSP.** Blocked by inline `onclick` plus the inline `<script>`. Chicken-and-egg with F2 below —
doing the event-delegation work is what makes a CSP possible.

**Escaping has a second hole.** The stated convention is "every user string goes through `esc()`",
and `esc()` deliberately does not escape `'`. But values interpolated into an *attribute*
(`value="${st.w}"` in the set rows) are not escaped at all, and `validateBackup()` checks the
*shape* of an imported file, never the types inside it — a hand-edited backup can put anything in a
set's `w`. Low severity today (only Ian imports backups) but the convention claims cover it does not
have, and the next agent will trust the convention.

**CI publishes the whole repo.** `path: '.'` in `deploy.yml` uploads `test/`, `CLAUDE.md` and this
file to the live site. Nothing leaks — the repo is public — but it is noise on the served surface.

## Still open — foundation

### F1. The schema is written in five places and nowhere *(highest value)*

To know what a "session" is you must read `blank()`, `MIGRATIONS`, `mergeDB()`, `validateBackup()`
and the `liveSessions()` filter. Adding one new tracked thing means editing all five, correctly.

Look at the bug history in `CLAUDE.md`. It is all one bug:

- `mobilityLog` — merge rule forgotten, absence read as "off"
- Migration 15 — `touch()` and persist forgotten, silently reverted in production
- Soft delete — "a missed filter ghosts a deleted row back into a view"
- The draft crash above — a field the views assume, unguarded on every path but one

Those are not four bugs. They are one: **the rules for a collection are implicit, so each new
collection re-learns them by failing in production.**

The fix is a single declaration the other five places derive from:

```js
const COLLECTIONS = {
  sessions:    { kind:'list', key:'id', soft:true,  sortBy:'date' },
  weights:     { kind:'list', key:'id', soft:true,  sortBy:'date' },
  mobilityLog: { kind:'map',  merge:'newer-wins', explicitFalse:true },
  lawnLog:     { kind:'map',  merge:'newer-wins', explicitFalse:true },
  // ...
};
```

Adding a feature becomes one line instead of five edits, and the merge rule cannot be forgotten
because there is nowhere left to forget it. **Constraint:** anything reached from `normalize()` runs
at module-eval time, so it must not touch a `const` declared further down — that temporal-dead-zone
trap has already taken out the boot once and is warned about twice in the file.

### F2. Inline `onclick` forces 326 global functions

Every handler must be a `window` global because the markup calls it by name. No namespacing, silent
collisions, no CSP possible, and it is the root of the apostrophe footgun. One delegated listener on
`#app` reading `data-act` / `data-arg` removes all of it at once. Mechanical, testable, and it needs
no build step.

### F3. `CLAUDE.md` gives the war stories but not the recipe

It says what breaks and why, which is genuinely excellent. It does not say *"to add a new tracked
thing, do these six steps in this order."* An agent following a numbered recipe beats an agent
inferring one from incident reports.

### F4. Line endings are unmanaged

`index.html` is CRLF on disk, the tests are LF, there is no `.gitattributes`, and `core.autocrlf` is
rewriting them on every touch. Adding `* -text` would make git store bytes exactly — and would
produce a 4,131-line diff on the next commit of `index.html`. That is a deliberate decision, not
something to slip into a cleanup commit. **Left untouched on purpose.**

### F5. The single-file rule should stay

330KB is a lot to hold in context, but the file is genuinely well-sectioned, and splitting it means a
build step, which is the thing that makes the app editable without a toolchain. F1–F3 buy more than
splitting would. Recommendation: leave it.

## Open questions for Ian

Unanswered as of this writing. Several of them can shrink the scope above considerably, so ask before
planning around them.

1. **Is cloud sync worth Firebase?** Two devices, one user. It brings open signup, unversioned rules,
   a three-file CDN dependency and the union-merge complexity that already destroyed four days of
   weigh-ins. Export/import already exists. What does live sync buy that is worth that surface?
2. **`draft` is a single object.** Start a workout on one device while another syncs — whose draft
   wins? The merge guards a corrupt `workout` name but there is no two-device draft story. Has this
   ever actually happened?
3. **What is the app for now?** It began as a skincare guide. It is now workouts, bodyweight, cardio,
   pet weight, lawn scheduling, weather, journal, todos, hobby picker and ideas. Every one is a
   collection needing merge rules. If "one app for my whole life" is the goal, F1 stops being
   nice-to-have.
4. **The lawn scheduler is the most complex logic in the app** and it is about grass. Does it earn
   its footprint?
5. **What is localStorage actually at?** Snapshots and the DB share roughly 5MB. The ring is capped
   at 700KB and quota failure is handled, but nobody has measured the real size or the growth curve.
6. **Why email/password auth?** Google sign-in has no signup surface to close, no password to leak
   and no `authErr()` mapping to maintain.

## Suggested phase order

1. **F1 — the `COLLECTIONS` spec.** Highest leverage, and it retires a whole bug class.
2. **F3 — the recipe in `CLAUDE.md`.** Cheap, and it compounds with F1.
3. **F2 — event delegation.** Unlocks a CSP and closes the escaping holes permanently.
4. **F4 — `.gitattributes`.** Its own commit, on its own, never bundled.

Answer the open questions before planning 1, because 3 and 6 can change what is worth building.
